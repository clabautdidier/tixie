# Requirements: User Management & Authentication - Project Tixie

Dit document bevat de functionele en technische vereisten voor de fundering van de Tixie ITSM-applicatie.

---

## 1. Rollenstructuur (RBAC)

De applicatie maakt gebruik van fijnmazige rollen om toegang tot specifieke ITIL-modules te beheren.

| Rol | Omschrijving | Portal |
| :--- | :--- | :--- |
| **ROLE_ADMIN** | Volledige systeemtoegang, inclusief User Management. | Admin |
| **ROLE_SUPERVISOR** | Kan tickets en assets van directe ondergeschikten inzien. | Admin/Customer |
| **ROLE_CONFIGADMIN** | Volledige schrijfrechten op CMDB (Locaties + Items). | Admin |
| **ROLE_CONFIGLOCATIONADMIN** | Kan enkel locaties aanmaken, aanpassen en verwijderen. | Admin |
| **ROLE_CONFIGITEMADMIN** | Kan enkel Configuration Items (assets) beheren. | Admin |
| **ROLE_SERVICEDESK_AGENT** | Kan tickets aanmaken, opvolgen, oppikken en toewijzen. | Admin |
| **ROLE_SUPPORT_AGENT** | Kan tickets aanmaken en oplossen, maar **niet** herassigneren. | Admin |
| **ROLE_KNOWLEDGE_ADMIN** | Beheerder van de Knowledge Base (inclusief verwijderen). | Admin |
| **ROLE_KNOWLEDGE_EDITOR** | Kan KB-artikelen maken en editeren, niet verwijderen. | Admin |
| **ROLE_SERVICE_ADMIN** | Volledige controle over de Service Catalogus. | Admin |
| **ROLE_SERVICE_EDITOR** | Beperkt beheer van services (geen configuratie-wijzigingen). | Admin |
| **ROLE_USER** | Eindgebruiker: kan eigen tickets en assets zien. | Customer |

## 2. User Management Functionaliteiten

### Hiërarchie & Profiel
* **Manager Relatie:** Elke gebruiker kan gekoppeld worden aan een 'Manager' (Self-referencing relationship in de database). Dit is cruciaal voor de `ROLE_SUPERVISOR`.
* **Password Reset:** Zowel admins (voor anderen) als gebruikers (voor zichzelf) moeten een wachtwoordreset kunnen uitvoeren.
* **Account Status:** Gebruikers kunnen op 'Active' of 'Inactive' gezet worden.

### Authenticatie (JWT)
* **Configurabele Expiratie:** De `expiration_time` van de JWT moet via de `application.properties` (omgevingsvariabele) instelbaar zijn.
* **Payload:** De token moet de `username`, `roles` en de `display_name` bevatten.
* **Security:** Wachtwoorden worden onomkeerbaar opgeslagen middels de **BCrypt** hashing algoritme.

## 3. Technische Requirements (Backend)

* **Spring Security Integration:** Gebruik van een `OncePerRequestFilter` om de JWT te valideren bij elk binnenkomend request.
* **Hierarchical Logic:** In de service-layer moet logica aanwezig zijn die checkt of een `ROLE_SUPERVISOR` inderdaad de manager is van de gebruiker wiens data hij opvraagt.
* **Flyway Seeding:** De database moet bij eerste start gevuld worden met:
    * Een standaard admin (`admin`/`admin123`).
    * Ten minste één test-manager en twee ondergeschikten om de hiërarchie te testen.

### 3.1. Bootstrapping & Security
* **Auto-Provisioning:** Bij het opstarten controleert de backend of de tabel `users` leeg is. Zo ja, wordt er één account aangemaakt met `ROLE_ADMIN`. Het gegenereerde wachtwoord wordt eenmalig in de console gelogd.
* **JWT Filter:** Elk request naar `/api/**` (behalve `/api/auth/login`) wordt gecontroleerd op een geldig JWT in de `Authorization` header.
* **Configuratie:** De JWT-secret en vervaltijd zijn instelbaar via omgevingsvariabelen.

### 3.2. Admin Portal (Nginx Container 1)
* **Login:** Toegang via een Bootstrap-loginpagina.
* **Role-Based Menu:** Na login wordt de JWT geparsed. Enkel gebruikers met `ROLE_ADMIN` zien het menu-item "User Management".
* **User List:** Een pagina die de `GET /api/users` aanroept en de resultaten in een Bootstrap-tabel toont.

### 3.3. Customer Portal (Nginx Container 2)
* **Login:** Toegang voor elke geregistreerde gebruiker.
* **Profielbeheer:** Een scherm waar de gebruiker de eigen `full_name` en `email` kan bijwerken (`GET` & `PUT` naar `/api/users/me`).
* **Self-Service Password:** Een formulier om het eigen wachtwoord te wijzigen (vereist verificatie van het oude wachtwoord).

* `POST /api/auth/login` -> Geeft JWT terug.
* `GET /api/users` -> Lijst van gebruikers (Enkel voor `ROLE_ADMIN`).
* `GET /api/users/me` -> Gegevens van ingelogde gebruiker.
* `PUT /api/users/me` -> Eigen profiel updaten.
* `POST /api/users/me/password` -> Eigen wachtwoord wijzigen.

## 4. UI Requirements (Web Components)

* **`<tixie-nav>`:** Moet dynamisch items tonen/verbergen op basis van de rollen aanwezig in de JWT.
* **`<tixie-user-edit>`:** Component voor admins om rollen en de manager van een gebruiker aan te passen.
* **`<tixie-password-reset>`:** Een herbruikbare component voor het wijzigen van het wachtwoord (zowel voor self-service als admin-override).

---

## 5. Troubleshooting Scenario's voor Studenten

1. **"Access Denied":** Een `SUPPORT_AGENT` probeert een ticket te assigneren. De student moet troubleshooten waarom de API een 403 teruggeeft.
2. **"Token Expired":** Stel de expiratie in op 1 minuut en laat studenten de error-handling in de frontend schrijven om de gebruiker netjes naar de login-pagina te sturen.
3. **"Circular Hierarchy":** Wat gebeurt er als Gebruiker A de manager is van Gebruiker B, en Gebruiker B de manager van Gebruiker A? (Validatie-logica).
